# WS 同步协议：命令驱动的增量同步

管理面板的多窗口实时同步采用 WebSocket + **命令驱动的事件同步**,而非快照重拉。
本文档是已确认的设计定稿。

## 设计哲学：为什么是命令同步

多个管理面板窗口同时连着后端,任一面板发生写操作,所有面板要实时收敛。
核心决策:**广播"操作命令"(带 db id 的 delta),而不是广播"信号后各自重拉快照"。**

| | 快照重拉 | 命令同步（本方案） |
|:--|:--|:--|
| 传输 | 信号 + 全量重查 | 只发增量命令 |
| 前端 | 重建整个视图 | 按 id 在本地重放 |
| 局部状态(折叠/筛选) | 可能受影响 | **保留**，只动被操作的 id |
| 跨面板一致性 | 各自对齐 | 单一数据源 + 广播收敛 |
| 本质 | 快照同步 | **事件同步** |

**关于"全量 vs 增量重建"的澄清**：浏览器刷新 = 整个 JS 重新加载,本地状态清零,
无论如何 refresh 时都是全量重建,这是绕不开的。因此命令同步的价值**不在初始化那一下**,
而在:①持续期间不需要轮询/重拉;②跨面板单一数据源收敛;③tag 按需加载(只传用到的)。
不要在"避免重连时全量重建"上优化——那是伪目标。

## 传输层：WS 的原子指令语义

命令用 WebSocket 传输,天然承载"指令序列"语义——每次发一条带 db id 的原子操作,几乎无额外开销。
这与 HTTP 形成对照:HTTP 倾向闭包化(一次传输所有数据,哪怕浪费),适合消费场景;WS 是双向流、持久连接、低开销,适合这种面向专业场景的持久连接、原子化指令流。

## 命令协议（与 CLI 一致，数组形式）

命令是数组,首个元素是操作名,后续是参数（db 自增 id）。`web` 中产生的操作命令 = CLI 同款。

**写操作**（后端执行后**原样广播**给所有连接，含发起者）：
```
['tag_add',    tagId, pageId]   # 给 page 加一个 tag
['tag_remove', tagId, pageId]   # 从 page 移除一个 tag
['tag_create', parentId, name]  # 新建 tag 节点
['tag_rank',   pageId, rootId, k]   # 页在某 rank 轴设第 k 档（remove 旧 + add 新）
```

**读操作**（按需拉取，不广播）：
```
['tags', [1,2,3,4]]   # 批量取 tag（DB 按 IN(ids) 直接查）
['tag',  3]           # 单个 tag 信息（字典缺失时按需拉）
```

**写操作完成后，命令原样返回/广播**：`['tag_add', 2, 3]` 执行完 → 广播给所有连接 → 前端各自重放。
渲染一律用 db id；值从 tag 字典取，没有则发读取命令按需填充。

## tag 字典（按需加载）

后端/前端维护 `tag` 字典（`{id: payload}`），按需填充：

- page 的 tag 存储的是 **id**；
- 字典中没有的 id → 发 `['tag', id]` 或批量 `['tags', [ids]]` 拉取 → 存入 `{id: payload}`；
- tags 基本只增不减、变化少，可考虑缓存到浏览器 localStorage（**本期不做**）。

### 渲染：接收末端 id，沿 parent_id 链向上取节点数组

tag 渲染组件**只接收末端 tag 的 id**，从字典沿 `parent_id` 逐个取，得到**节点数组**（`末端 tag → 父 → 祖父 …`），由此拼出完整层级。字典每个节点带 `parent_id`，够组装。

**向上查链 = 链表遍历**，`parent_id` 即指针，O(深度) 且深度极浅，**无需缓存**。（组件是纯函数，对不可变字典输入自然稳定；但链本身廉价，缓存无收益。）

### 同级节点：惰性请求 + 会话缓存

渲染只需向上链（已有）；唯有点开下拉菜单（列出同级供切换）才需要"某父下所有子"。同级信息**不全量随字典附带**（每个 tag 背一串多数时用不到的 children_ids 违背"只拉需要的"），改用**惰性请求**：

- 渲染路径**不加载同级**——零成本；
- 点开菜单时才发 `['tag_children', parentId]` 拉该父的同级列表 → **缓存到会话级 `parent_id → children` Map**，同会话再点同父直接命中；
- 没点开的节点永远不拉（"90% 用不到"从负担变成优势）。

## 连接生命周期

1. **连接建立**：后端把连接加入活跃集合，推送初始视图。
2. **任意连接收到写命令**：后端执行 → 广播该命令给集合内所有连接 → 前端各自重放。
3. **连接断开**：立即从集合清除（send 失败即 discard），不阻塞其他连接。
4. 广播用锁串行化，防交错。

**广播推什么**：只推**命令本身**（增量），各面板收到后本地按 id 重放。不推完整数据——
强制覆盖各面板的局部状态（A 面板看 research 的 filter，B 操作 work → A 不应被刷新到 work）。

## 初始化流程

**核心：不全量拉 forest，只拉需要的。**

1. 一次拉 `pages`（含 tag_ids）。
2. 前端取所有 pages 的 tag_ids **并集**，一次 `['tags', [并集]]` 批量拉取，填字典。
3. **并集天然覆盖每个引用 tag 的所有上级**——tag 树结构依赖祖先链，父节点必在集合内。后端用一次**递归 CTE**（`WITH RECURSIVE`）从并集向上展开出完整祖先链，连同所有引用 tag 一次查回，字典因此一次就含全部 path 上级，无需再补拉。
4. **数据交给 pages 列表渲染前**，确保该页引用的 tag 及其中间层级已在字典中（递归 CTE 已保证）。

**rank 轴 / 菜单**：只加载被用到（被页面引用）的那些层级；未被引用的 tag 节点不加载。

## 交互从"整组替换"改为"增量原语"

UI 不做整组 set_tags 替换，改为语义化增量：

- 开一个 tag → `['tag_add', tagId, pageId]`
- 关一个 tag → `['tag_remove', tagId, pageId]`
- rank 改 3 星 → 先 remove 当前 rank 档位，再 add 第 3 档

前端按每条命令就地增删，不维护完整 tag_ids 数组再整体替换。
